어플리케이션 테스트 수행하기
테스트와 소프트웨어 개발 생명주기
소프트웨어 아키텍트와 테스트 매니저가 V 모델 상에서 서로 보완 관계를 형성한다
개발 순서 : 요구사항 분석 -> 아키텍처 설계 -> 모듈 설계 -> 구현
테스트 진행 순서 : 단위 테스트 -> 통합 테스트 -> 시스템 테스트 -> 인수 테스트

테스트는 개발 완료 후 시작하는 것이 아니라 각 개발 단계 산출물과 1:1로 대응
요구사항 분석 <-> 인수 테스트 : 사용자 요구사항 만족 여부 검증
아키텍처 설계 <-> 시스템 테스트 : 전체 시스템의 정상 작동 검증
모듈 설계 <-> 통합 테스트 : 모듈 간 연결 정상 작동 검증
구현 <-> 단위 테스트 : 개발 코드 및 모듈 정상 작동 검증

단위 테스트(Unit Test)
- 모듈, 컴포넌트 단위의 최소 기능 검증

모듈(Module) : 프로그램에서 특정 기능을 담당하도록 묶어놓은 코드 단위
ㄴ 로그인 기능(요청 -> controller -> service -> dao -> db)
컴포넌트(Component) : 프로그램을 구성하는 독립적인 기능 단위
ㄴ 회원 컴포넌트(로그인, 회원가입, 정보수정)

테스트 대상 : 하나의 메서드, 클래스, Service, 계산 로직, 데이터 변환 기능 등 ...

접근 방법
구조 기반 테스트(화이트박스) : 프로그램 내부 구조외 제어 흐름, 조건 결정, 예외 처리 경로 등을 코드를 알고 있는 상태에서 검증
명세 기반 테스트(블랙박스) : 내부 코드 대신 요구사항과 입출력 결과에 집중하며, 동등 분할과 경곗값 분석 기법을 활용

통합 테스트(Integration Test)
- 모듈 간 인터페이스 및 상호작용을 검증
- 개별 모듈이 정상이어도 연결 과정에서 발생하는 오류를 잡아낸다

시스템 테스트(System Test)
- 통합된 전체 시스템이 요구사항을 완전히 수행하지 실제 운영환경과 유사한 조건에서 검증

인수 테스트(Acceptance Test)
- 최종 사용자 및 업무 이해관계자가 실제 업무 운영 여부를 결정하기 위해 수행한다
- 단순 오류 실행 유무가 아닌 실제 업무 적용 가능성을 검증한다.

통합 테스트의 종류
1. 빅뱅 : 모든 모듈을 한꺼번에 결합
- 장점 : 세밀한 계획이 불필요. 모듈 수 적을 때 신속함
- 단점 : 오류 원인 추적이 어려움, 모든 모듈 개발 전까지 시작 불가
2. 상향식(Bottom Up) : 하위 모듈(DAO)부터 상위 모듈(Controller)로 결합
- 드라이버(Driver) : 미개발된 상위 모듈을 대신해 하위 모듈을 실행시키는 가짜 상위 모듈
- 장점 : 하위 모듈만 빠르게 검증할 수 있다
- 단점 : Driver를 별도로 작성해야 한다
3. 하향식(Top Down) : 상위 모듈부터 하위 모듈로 결합
- 스텁(stub) : 미개발된 하위 모듈 대신 미리 준비된 가짜 결과를 반환하는 임시 모듈
- 장점 : 화면/업무 로직을 빠르게 검증할 수 있다.
- 단점 : Stub의 별도 작성이 필요하다
4. 샌드위치 : 상향식과 하향식을 동시에 진행하여 종간 계층에서 연결
- Drivere와 Stub을 모두 사용한닫
- 테스트 기간 단축 및 병렬 진행
5. 중앙식 : 중앙 통제 모듈(Hub)을 중심으로 모듈 간 데이터 전달 및 제어 수행
6. 협업식 : 모듈 간 직접 연계하여 실제 운영 환경과 유사하게 연계성 검증
7. 레이어 통합 : 계층 단위로 결합하여 인접 계층 및 전체 구조 검증

시스템 테스트 방법
1. 기능 요구사항 테스트 : 시스템이 수행해야할 기능에 대한 명세 기반 블랙박스테스트
- 회원가입을 할 수 있어야 한다
- 상품을 조회할 수 있어야 한다
- 주문을 취소할 수 있어야 한다
2. 비기능 요구사항 테스트 : 성능 회복, 보안, 네비게이션 구조 등 이트박스 및 비기능 요소 검증
- 조회 결과는 3초 이내 표시되어야 한다
- 동시에 1000명이 접속할 수 있어야 한다
- 사용자 비밀번호는 암호화되어야 한다
- 서버 장애 10분 이내에 복구되어야 한다

인수 테스트
- 개발이 왼료돤 시스템의 최종 사용 운영 기능 여부를 결정하는 6가지 테스트
사용자 인수 테스트 : 비즈니스 사용자가 업무 사용의 적절성을 확인
운영상의 인수 테스트 : 시스템 관리자가 백업,/복원, 재난 복구, 정기 점검ㄷ 등 확인
계약 인수 테스트 : 계약상의 인수 및 검수 조건 준수 확인
알파 테스트 : 개발 조직 내부의 잠재 고객이 수행
베타 테스트 : 실제 환경에서 외부 사용자가 수행

설계 하는 화이트 박스 테스트 기법
- 단순히 어떤 입력에 어떤 결과가 나오는지만 확인하는 것을 너머, 내부의 제어 흐름ㄷ과
구문들이 실제로 실행되는지를 검증한다
각 명령문이 실행되었는가?
IF문의 참 거짓 경로가 모두 실행되었느가?
복합 조건식의 개별 조건이 참과 거짓을 모두 가졌는가?
반복문의 내부와 종료 경로가 실행되었는가
실행 가능한 조유 경로가 충분히 테스트 되었는가

구조 기반 테스트의 세부 커버리지  유형
커버리지 : 테스트가 프로그램을 얼마나 빠짐없이 확인했는가?

구문 커버리지
- 프로그램 내부의 모든 문장을 최소 한 번 이상 실행하도록 테스트 케이스 구성

조건 커버리지
- 조건식 안에 포함된 개별 조건이 참과 거짓을 적어도 한 번씩 갖도록 테스트 케이스를 작성한다

결정 커버리지
- 전체 조건식의 결과가 참과 거짓이 되는 상황을 각각 최소 한 번 이상 실행한다

조건/결정 커버리지
- 개별 조건식도 참/거짓을 모두 만족하고, 전체 조건식도 참/거짓을 모두 만족하도록 결합한 기법

변경 조건/결정 커버리지
- 다른 개별 조건의 결과에 영향을 받지 않고, 해당 개별 조건 단 하나에 의해
전체 결정 결과가 달라지는 경로를 검증한다

다중조건 커버리지
- 조건식 내 개별 조건들의 가능한 모든 논리적 조합을 전부 테스트한다


2. 명세 기반 테스트
- 소스코드를 보지 않고, 요구사항 명세서, 설계서, 비즈니스 규칙 등 소프트웨어 명세서를 바탕으로 
입출력 결과를 검증하는 블랙박스 테스트 기법
- 개발자 시점이 아닌 사용자 및 기획자 시점에서 시스템이 요구된 대로 동작하는지 검증한다

동등 분할
- 입력값 영역을 유효한 갑소가 유효하지 않은 값의 균등한 그룹으로 나누고, 
각 그룹에서 대표값 하나씩을 선정하여 테스트한다
- 최소한 테스트 케이스로 전체 입력 역을 효율적으로 커버한다

경계값 분석
- 오류가 발생하기 가장 쉬운 경계 부근의 값(경계값, 경계 바로 위/아래 값을)을 집중적으로 테스트한다
- 14세 이상 -> 13,14,15세를 테스트

결정 테스트 텟트
- 복잡한 조건 조합과 그에 따른 행동을 표 형태로 정리하여 모든 비즈니스 규칙 조합을 검증한다

상태 전이 테스트
- 시스템의 상태 변화와 이벤트에 따른 상태 이행 과정을 검증한다

유스케이스 테스트
- 실제 사용자의 이용 시나리오 흐름에 따라 기본 흐름과 대안 흐름, 예외 흐름을 테스트한다


3. 경험 기반 테스트
- 명세서나 코드 구조에 의존하지 않고 테스터의 지식, 경험, 직관 과거 결함 이력을 바탕으로
수행하는 테스트 기법

탐색적 테스트
- 테스트 케이스를 미리 작성하지 않고, 테스트 수행 과정에서 얻은 시스템 이해를 바탕으로
테스트 설계와 실행을 동시에 진행한다

리스크 기반 테스팅
- 모든 기능을 동일한 비중으로 테스트하지 않고, 문제가 발생할 간으성이 높거나 문제가 발생했을 때
피해가 큰 기능을 우선적으로 테스트하는 방법

테스트 자동화
- 소프트웨어 테스트는 시간과 비용이 많이 든다
- 테스트의 정확성을 유지하려면 시간과 비용을 줄일 수 있는 자동화 도구가 중요해졌다
- 같은 기능을 여러번 반복해서 테스트해야 하는 경우 사람이 직접 숳애하면 많은 시간이 필요하다
- 프로그램이 수정될 때마다 이를 다시 수행해야 하므로 자동화 도구를 사용하면
반복 작업을 줄일 수 있다.

- 테스트 자동화는 사람이 수행하던 반복적인 테스트 절차를 자동화 도구로 준비, 구현, 수행, 분석하도록
스크립트 형태로 구현하는 것이다.

테스트 자동화의 흐름
1. 테스트 조건 정의
2. 자동화 스크립트 작성
3. 테스트 실행
4. 실제 결과 수집
5. 예상 결과와 비교
6. 결과 보고서 생성

자동화가 적합한 테스트
- 반복적으로 수행하는 테스트
- 회귀 테스트
- 많은 데이터를 사용하는 테스트
- 성능 테스트
- API 테스트
- 여러 환경에서 반복되는 테스트

테스트 도구의 장점
- 테스트 데이터 재입력 및 재구성과 같은 반복작업을 자동화하여 인력과 시간을 줄인다
- 요구사항 정의, 성능 및 스트레스 테스트, 품질 측정을 최적화한다
- 빌드 확인, 회귀 테스트, 다중 플랫폼 호환성, 소프트웨어 구성 및 기본 테스트 등의 품질을 향상한다

단점
- 도구 전문가를 양성하거나 고용해야한다
- 초기 프로세스 적용에 시간, 비용, 노력이 추가로 필요하다
- 비공개 상용 도구는 가격이 높을 수 있다
- 인력과 교육에 대한 유지관리 비용이 발생한다
- 자동화 도구를 도입한다고 즉시 테스트 비용이 줄어드는 것은 아니다.
- 화면 구조가 자주 변경되면 자동화 스크립트도 계속 수정해야 하므로 오히려 유지보스
비용이 증가할 수 있다.

테스트 도구 평가 방법 및 요소
평가 방법
- 테스트 도구가 지원하는 기능을 종류별로 나열하고 기록한다
- 테스트 요소의 목표값이나 평균값을 설정한 후 해당 기준에 따라 평가한다
- 비용을 줄이기 위해 일부 필수 요솬 고려해야 한다면 최소한의 요구사항을 만족하는 도구를 선정한다

평가 요소
- 사용 편의성
- 다중 사용자 접속
- 결함 추적
- 도구 기능성
- 보고 능력
- 성능 및 스트레스 테스트
- 버전 제어
- 테스트 계획과 관리
- 가격
- 테스트 도구 제조사의 지원 능력

어플리케이션 테스트 수행하기
테스트 계획서를 확인한다
- 기존에 작성된 테스트 기획서를 활용하여 사용자 요구사항을 일관성있게 계획, 설계,
실행할 수 있도록 전체 테스트 순서와 방법을 확인한다

테스트 목적과 범위의 확인
테스트 목적
- 프로그램 기능의 정확성
- 프로그램 기능의 완전성
- 예외 상황 처리의 적절성
- UI 표준 준수 여부
- 개발 표준 준수 여부

테스트 범위
- 성능 테스트 기간과 진행 자원에 따라 달라질 수 있다
- 테스트 범위를 정하지 않으면 제한된 일정 안에 모든 기능을 확인하려다가 중요한 기능을
충분히 테스트하지 못할 수 있다

범위 선정 기준
- 업무 중요도가 높은 기능
- 장애 발생 시 영향이 큰 기능
- 최근 변경된 기능
- 외부 시스템과 연계되는 기능
- 데이터 처리량이 많은 능
- 사용 빈도가 높은 기능

테스트 실행 계획을 확인한다
테스트 시작 기준과 종료 기준을 확인한다
- 개발 진적률이 50% 이상일 때 단위 테스트를 시작한다
- 오류가 얼마나 남았는지 완벽하게 알 수 없으므로 테스트를 종료할 기준을 미리 정한다
ㄴ 모든 단위 시험 케이스가 성공적으로 기록된 경우
ㄴ 일부 케이스가 통과하지 않았지만 형향이 제한적이라고 판단되는 경우
ㄴ 중대한 결함이 만족스럽게 조치되고, 재테스트에서 해결된 것으로 판단되는 경우
ㄴ 수정되지 않은 결험이 존재하더라도 전체 거토 결과 영향이 제한적이라고 확인되는 경우

테스를 종료한다는 것은 결함이 하나도 없다는 의미가 아니다

- 각 담당자의 역할과 보고 체계를 확인한다

기술 지원 : 테스트 방법 교육, 환경과 도구 지원

테스트 케이스를 확인한다
- 테스트 케이스로 선정된 주요 업무는 테스트 시나리오에 따른 세부적인 업무 처리 절차를 정의한다

- 실제 운영 데이터를 사용할 경우 문제가 발생할 수 있다
ㄴ 실제 고객 데이터 변경 또는 삭제

ㄴ 테스트 주문이 실제 매출에 반영됨
ㄴ 테스트 메시지가 실제 고객에데 발송된
ㄴ 데이터 복구가 어려움

테스트 환경을 확인한다
- 테스트 대상 장비와 주요 사양을 확인한다

어플리케이션 결함 관리
결함
- 프로그램과 명세서 간의 차이 또는 업무 내용의 불일치
- 기대 결과와 실제 관찰 결과 간의 차이
- 시스템이 사용자가 기대하는 타당한 수준을 충족하지 못해 변경이 필요한 모든 사항
- 요구사항에 있는 기능이 구현되지 않음
- 계산 결과가 잘못됨
- 버튼을 눌러도 반응하지 않음
- 화면의 용어가 요구사항과 다름
- 데이터가 DB에 저장되지 않음

결함 관리 프로세스
1. 결함 관리 계획
- 전체 프로세스에서 결함 관리에 필요한 일정, 인력 및 업무 프로세스를 확보하여 
계획을 수립하는 활동이다
- 결함 관리 계획에서는 다음의 사항을 결정한다
ㄴ 결함을 어디에 기록할 것인가
ㄴ 누가 결함을 등록할 것인가
ㄴ 누가 결함을 검토할 것인가
ㄴ 누가 수정할 것인가
ㄴ 심각도와 우선순위를 어떻게 구분할 것인가
ㄴ 결함 처리 상태는 어떻게 관리할 것인가
ㄴ 재시험은 누가 수행할 것인가
ㄴ 결함 보고서를 언제 작성할 것인가
2. 결함 기록
- 테스터는 발견된 결함의 정보를 관리 데이터베이스에 기록한다
3. 결함 검토
- 등록된 결함의 주요 내용을 검토하고, 결함을 수정할 개발자에게 전달한다
ㄴ 실제 결함이 맞는가
ㄴ 요구사항을 잘못 이해한 것은 아닌지
ㄴ 동일한 결함이 이미 등록되어 있지 ㅇ낳은지
ㄴ 결함을 재현할 수 있는지
ㄴ 기록된 정보가 충분한지
ㄴ 어떤 모듈에서 발생했는지
ㄴ 심각도와 우선순위가 적절한지
ㄴ 어느 개발자에게 배정할 것인지
- 결함이 아닌 것으로 판정되거나 동일한 결함이 이미 존재하면 수정 대상에서 제외
4. 결함 수정
- 개발자는 자신에게 할당된 결함이 발생한 프로그램을 수정한다
ㄴ 결함의 근본 원이
ㄴ 수정 대상 코드
ㄴ 관련된 다른 기능
ㄴ 수정으로 발생할 수 있는 부작용
ㄴ DB 또는 설정 파일의 변경 여부
ㄴ 테스트 케이스 수정 필요 여부
ㄴ 문서 변경 필요 여부
- 단순히 오류 메시지를 없애는 것이 아니라 오류가 발생한 근본 원인을 제거해야 한다

5. 결함 재확인
- 테스터는 개발자가 수정한 내용을 확인하고 다시 테스트한다
- 결함 재확인은 수정된 기능이 정상적으로 동작하는지를 확인하는 재시험
ㄴ 재시험 : 발견되었던 결함이 실제로 해결되었는지 확인
ㄴ 회귀테스트 : 수정으로 인해 기존 정상 기능에 새로운 문제가 발생하지 않았는지 확인

6. 결함 상태 추적 및 모니터링
- 결함 관리 팀장은 결함 관리 데이터베이스를 이용하여 대시보드 또는 게시판 형태의 서비스를 제공한다

7. 최종 결함 분석 및 보고서 작성
- 발견된 결함 내용과 이해관계자의 의견을 반영한 보고서를 작성하고 결함 관리를 종료한다


결함의 상태 및 추적
- 결함은 발견된 후 수정하고 종료될 때까지 여러 상태로 변경한다

1. 결함 등록(Open)
- 테스터 또는 QA 담당자가 결함을 처음 발견하여 등록했지만 아직 분석되지 않은 상태

2. 결함 검토(Reviewed)
- 등록된 결함을 담당 모듈 개발자, 테스터, 프로그램 리더 및 QA 담당자가 검토하는 상태

3. 결함 할당(Assigned)
- 결함의 영향 분석과 수정을 위해 개발자 또는 문제 해결 담당자에게 할당된 상태

4. 결함 수정(Resolved)
- 개발자가 결함 수정을 완료한 상태

5. 결함 조치 보류(Deferred)
- 수정이 필요한 결함이지만 현재 수정할 수 없어 연기된 상태
- 우선순위와 일정을 고려하여 이후 재오픈을 준비한다

6. 결함 종료(Closed)
- 결함이 해결되고 테스터와 QA 담당자가 종료를 승인한 상태

7. 결함 해제(Clarified)
- 테스터, 비교 프로그램 리더 및 QA 담당자가 검토한 결과 결함이 아닌것으로 판명된 상태

결함 분류
1. 시스템 결함
- 어플리케이션 환경이나 데이터베이스 처리에서 발생하는 결함
ㄴ 비정상적인 종료 또는 중단
ㄴ 응답 시간 지연
ㄴ 데이터베이스 오류
2, 기능 결함
- 기획, 설계 또는 업무 시나리오 단계에서 발생한 문제이다.
ㄴ 요구사항 미반영 또는 불일치
ㄴ 부정확한 비즈니스 프로세스
ㄴ 스크립트 오류
ㄴ 다른 시스템 연동 오류
3. GUI 결함
- 사용자 화면 설계에서 발생하는 결함
ㄴ UI 비일관성
ㄴ 부정확한 커서 또는 메시지
ㄴ 데이터 타입 표시 오류
4. 문서 결함
- 기획자, 사용자 및 개발자 간 의사소통과 기록이 원활하지 않아 발생한다
ㄴ 온라인, 오프라인 사용자 메뉴얼 불일치
ㄴ 요구사항 분석서와 기능 요구사항의 불일치
ㄴ 내용이 누락된 불완전한 문서

결함심각도
- 결함이 전체 시스템에서 미치는 영향을 수준별로 나타낸 것
1. High
- 시스템이 중단되거나 더 이상 업무를 진행할 수 없는 결함
ㄴ 핵심 요구사항 미구현
ㄴ 시스템 다운
ㄴ 장시간 응답 지연
ㄴ 시스템 복구 후 데이터 왜곡
2. Medium
- 시스템의 업무 흐름에 영향을 미치는 결함
3. Low
- 시스템 흐름에 직접적인 영향을 미치지 않는 결함
ㄴ 부정확한 GUI
ㄴ 부정확한 메시지
ㄴ 오류 메시지 미출력
ㄴ 화면 문법 또는 철자 오류
ㄴ 화면 구성 오류

문제 1. 테스트 단계 판단

온라인 쇼핑몰의 주문 기능을 개발하고 있다.

개발자는 다음 메서드가 상품 가격과 주문 수량을 이용하여 정확한 주문 금액을 계산하는지 확인하려고 한다.

public int calculateTotalPrice(int price, int count) {
    return price * count;
}

테스트할 때 데이터베이스, Controller, 다른 Service와의 연결은 사용하지 않고 해당 메서드만 독립적으로 검증하려고 한다.

문제

위 상황에서 수행해야 할 테스트 종류를 작성하고, 그렇게 판단한 이유를 2가지 이상 서술하시오.

- 단위 테스트
1. calculatorTotalPrice()라는 하나의 작은 기능 단위를 독립적으로 테스트하기 때문
2. DB나 다른 모듈과의 연결을 제외하고 해당 메서드 자체가 올바르게 동작하는지 확인하기 때문
3. 프로그램 전체가 아닌 계산 로직만 검증하기 때문

문제 2. 통합 테스트 적용

Spring Boot로 회원 조회 기능을 개발하였다.

각 모듈을 개별적으로 테스트한 결과는 다음과 같다.

MemberController : 정상
MemberService    : 정상
MemberDAO        : 정상
Database         : 정상

하지만 실제로 다음 흐름을 연결하여 회원 조회를 실행하자 잘못된 회원이 조회되었다.

사용자 요청
   ↓
Controller
   ↓
Service
   ↓
DAO
   ↓

문제 6. 구문 커버리지와 결정 커버리지 판단

다음 코드를 테스트한다.

public int calculateDiscount(int price) {

    int discount = 0;

    if (price >= 50000) {
        discount = 5000;
    }

    return price - discount;
}

다음 테스트 하나만 수행하였다.

입력 : 60000
결과 : 55000
문제

위 테스트 결과에 대해 다음 두 가지를 각각 판단하고 이유를 작성하시오.

구문 커버리지는 100%인가?
결정 커버리지는 100%인가?

결정 커버리지 100%가 아니라면 추가할 테스트 데이터를 하나 작성하시오.

구문 커버리지는 100%이다.
60,000을 입력하면 메서드 안에 실행 가능한 구문이 모두 실행된다
결정 커버리지는 100%가 아니다.
조건식의 결과 중 거짓 결과를  실행하지 않았기 때문이다.
40,000을 넣어서 결과를 확인한다

문제 7. 조건 커버리지 분석

다음 조건문을 테스트하려고 한다.

if (isMember || hasCoupon) {
    discount();
}

개별 조건은 다음과 같다.

조건 A : isMember
조건 B : hasCoupon

다음 두 테스트를 수행하였다.

테스트   A   B   전체 결정
1   True   False   True
2   False   True   True
문제

위 테스트에 대하여 다음을 각각 판단하고 그 이유를 서술하시오.

조건 커버리지 100%를 만족하는가?
결정 커버리지 100%를 만족하는가?

결정 커버리지를 만족하지 않는 경우 어떤 테스트를 추가해야 하는지도 작성하시오.

조건 커버리지는 100% 만족한다
조건 A는 TRUE, FALSE를 모두 가지고 조건 B도 TRUE, FALSE를 모두 가지기 때문이다.
결정 커버리지는 100%가아니다.
전체 결정 결과가 FALSE가 되는 테스트를 추가해야 한다

문제 8. 경험 기반 테스트 적용

쇼핑몰 주문 기능의 기본 테스트는 다음과 같이 작성되어 있다.

상품 선택
→ 장바구니 등록
→ 주문 버튼 클릭
→ 주문 완료

정상적인 주문 테스트는 이미 완료하였다.

테스터는 과거 쇼핑몰 시스템에서 다음과 같은 문제가 자주 발생했던 경험이 있다.

버튼을 연속 클릭했을 때 중복 데이터 생성
네트워크 장애 중 데이터 저장 오류
비정상적으로 큰 수량 입력에 대한 오류
문제

위 경험을 바탕으로 주문 기능에 추가할 경험 기반 테스트 3가지를 작성하고, 각각 어떤 문제를 발견하기 위한 테스트인지 서술하시오.

주문 버튼 연속 클릭
- 주문 버튼을 짧은 시간동안 두 번 이상 연속해서 클릭한다
- 하나의 주문이 여러 건으로 중복 생성되는지 확인한다
주문 중 네트워크 연결 해제
- 주문 저장이 진행되는 동안 네트워크 연결을 끊는다
- 데이터가 일부만 저장되거나 주문이 중복 처리되는 문제가 발생하는지 확인한다
비정상적으로 큰 주문 수량 입력
- 수량에 9,999,999같은 값을 입력한다
- 허용되지 않은 입력에 대해 오류 처리 및 입력 제한이 정상적으로 수행된지 확인한다

5 : 장애 발생 후10분 이내 복구 -> 서버 장애를 발생시킨 후 정해진 시간 안에 정상 상태로 돌아오는지

문제 10. 요구사항 기반 테스트 케이스 종합 설계

온라인 교육 시스템에 다음 요구사항이 있다.

수강신청 요구사항
학생은 원하는 강좌를 신청할 수 있다.
하나의 강좌에는 최대 30명까지 신청할 수 있다.
이미 30명이 신청한 강좌에는 추가 신청할 수 없다.
동일한 학생은 동일한 강좌를 두 번 신청할 수 없다.
신청이 성공하면 수강신청 목록에 해당 강좌가 표시되어야 한다.

현재 상황은 다음과 같다.

강좌명 : Java Programming
현재 신청 인원 : 29명

학생 1001 : 해당 강좌 신청 이력 없음
학생 1002 : 해당 강좌 이미 신청함
문제

위 요구사항을 검증하기 위해 다음 3개의 테스트 케이스를 작성하시오.

정상 수강신청
최대 인원 초과
중복 수강신청

각 테스트 케이스에는 반드시 다음 항목을 작성하시오.

사전조건
수행 내용
예상 결과


정상 수강신청 : 현재 29명, 1,001은 미신청 -> 학생 1,001이 수강신청
-> 예상 결과 신청 인원 30명, 수강신청 목록에 강좌 표시

최대 인원 테스트에서는 이미 30명이 신청한 상태에서 추가 학생이 신청하면 시스템이
신청을 거부해야 한다

중복 신청 테스트에서는 이미 같은 강좌를 신청한 학생이 다시 신청할 경우 

두 번째 신청이 등록되지 않아야 한다
