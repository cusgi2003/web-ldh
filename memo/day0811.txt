테스트 자동화 수행 시의 고려사항

- 재사용 및 측정이 불가능한 테스트 프로그램은 제외
- 반복적인 빌드에서 스크립트 재사용성이 가능해야 한다
- 모든 수동 테스트 과정을 자동화 할 수는 없다
- 도구 환경 설정과 도구 습득 기간을 고려하여 프로젝트 지연을 방지해야 한다
- 테스트 엔지니어를 늦게 투입하면 프로젝트에 대한 이해 부족으로 불완전한 테스트를
초래할 수 있으므로, 적절한 투입시기와 계획을 프로젝트 초기에 수립해야 한다


테스트 도구 평가 방법 및 요소

평가 방법
- 도구가 지원하는 모든 사항에 대해 종류별로 나열,기록
- 테스트에 해당하는 요소에 대한 목표 또는 평균값을 설정하고 설정된 기준으로 평가
- 비용을 최소화 하기 위해 필수적인 몇 가지 요소만을 고려해야 할 경우 최소한
요구사항을 만족하는 도구 선정

평가 요소
ㄴ 객관적이고 수치화되는 항목을 이용하여 평가
	- 도구의 사용 편의성
	- 다중 사용자 접속
	- 결함 추적
	- 도구 기능성
	- 보고 능력
	- 성능 및 스트레스 테스트
	- 버전 제어
	- 테스트 계획과 관리
	- 가격

어플리케이션 테스트 수행하기

1. 테스트 계획서 확인하기
- 테스트의 목적과 범위를 확인하기
ㄴ 목적 : 업무흐름별 경로의 적절성, 각 어플리케이션 간 연계 및 연동 확인, 기능과 비기능의
적합성 및 사용편의성 확인
ㄴ 범위 : 기간과 자원에 따라 범위가 달라진다 5일간의 일정으로 진행할 때, 적게는 5개에서
10개 이내의 기능을 선정하여 테스트한다.

- 테스트 실행 계획을 확인한다
ㄴ 시작, 종료 기준을 확인한다
	시작 : 개발 진척률이 50% 이상일 때 단위 테스트 시작
	종료 : 중대한 결함이 조치되건, 결함의 영향이 크지 않으면 종료
ㄴ 테스트 수행 절차 확인 : 테스트 관리자, 업무 그룹, 기술 지원 등의 역할과 고보 체계를 확인한다

- 테스트 케이스를 확인한다
ㄴ 테스트 시나리오 확인하기
ㄴ 테스트 케이스 확인하기

- 테스트 데이터확인하기
ㄴ 테스트 진행되는 동안 데이터의 변경(생성/수정/삭제) 작업이 발생할 수 있으므로, 테스트 상황에
맞는 테스트 데이터의 생성 및 유지 방침을 확인해야한다
ㄴ 테스트 수행 시 별도의 테스트 데이터가 구성되면 좋으나 만일 실운영 데이털르 사용할 경우엔느 특히
데이터의 유지 절차를 고려해야 한다.

- 테스트 환경을 확인한다
ㄴ 테스트 대상 장비, 테스트 도구, 테스트용 데이터, 네트워크 환경 등 테스트와 관련된 일반적인
IT 자원과 도구를 명시하고, 자원별 담당 부서는 사전 점검 항목을 참고하여 테스트 수행을 위한
최소 수준 이상의 구성 여부를 확인한다.
ㄴ 테스트에 사용할 도구를 확인한다
도구들을 테스트 단계에 따라 분류하면 테스트 생성, 수행, 관리 도구로 나뉜다.

테스트 생성 도구 : 테스트를 준비하는 단계에서사용하는 도구( 테스트 문서, 테스트 데이터, 테스트 케이스,
테스트 조건)

테스트 수행 도구 : 실제 프로그램을 실행하면서 테스트 하는 도구 


어플리케이션 결함 관리
결함
1. 프로그램 명세서 간의 차이, 업무 내용 불일치
2. 기대 결과와 실제 관찰 결과 간의 차이
3. 시스템이 사용자가 기대하는 타당한 기대치를 만족시키지 못할 때 변경이 필요한 모든 것

결함 관리 프로세스
1. 결함 관리 계획
- 전체 프로세스에서 결함 관리에 대한 일정, 업무, 프로세스를 확보하여 
계획을 수입하는 것
2. 결함 기록
- 테스터는 발견된 결함에 대한 정보를 결함 관리 DB에 기록
3. 결함 검토
- 등록된 결함에 있어서 주요 내용을 검토하고, 결함을 수정할 개발자에게 전달한다
4. 결함 수정
- 개발자는 할당된 결함의 프로그램을 수정한다
5. 결함 재확인
- 테스터는 개발자가 수정한 내용을 확인하고 다시 테스트를 수행한다
6. 결함 상태 추적 및 모니털이 활동
- 결함 관리 팀장은 결함 관리 데이터베이스를 이용하여 대시보드 또는
게시판 형태의 서비스를 제공한다
7. 최종 결함 분석 및 보고서 작성
- 발견된 결한에 대한 내용과 이해관계자들의 의견이 반영된 보고서를 작성하고 
결함 관리를 종료한다


결함의 상태 및 추적
결함은 여러 상태를 가지고 있으며, 이 상태의 변화를 지속저그오 추적 관리하는 것이 결함 관리의
주요 작업 중 하나이다.

1. 결함 등록(Open)
- 테스터와 품질 관리 담담장에 의해 결함이 처음 발견되어 등록되었지만,
아직 분석되지 않은 상태
2. 결함 건토(Reviewed)
- 등록된 결함을 담당 모듈 개발자, 테스터, 프로그램 리더, 품질 관리 담당자와 검토하는 상태
3. 결함 할당(Assigned)
- 결함의 영향 분석 및 수정을 위해 개발자와 문제 해결 담당자에게 할당된 상태이다
4. 결함 수정(Resolved)
-  개발자에 의해 결함의 수정이 완료된 상태이다
5. 결함 조치 보류(Deferred)
- 수정이 필요한 결함이지만 현재 수정이 불가능해서연기된 상태로서 
6. 결함 종료(Closed)
- 발견된 결함이 해결되고 테스터와 품질 관리 담당자에게 의해 종료 승인을 한 상태이다
7. 결함 해제(Clarifed)
- 테스터, 프로그램 리더, 품질 관리 담당자가 결함을 검토한결과, 결함이 아니라가 판명된 경우


결함의 분류

시스템 결함
- 비정상적인 종료/중단
- 응답시간 지연
- 데이터베이스 에러

기능결함
- 요구사항 미반영/불일치
- 부정확한 비즈니스 프로세스
- 스크립트 에러
- 타 시스템 연동 시 오류

GUI 결함
- 응용 프로그램 UI 비일관성
- 부정확한 커서/메시지
- 데이터 타입의 표시 오류

문서 결함
- 기획자, 사용자, 개발자 간의 의사소통과 기록이 윈활하지 않은 경우에 발생하는 결함
- 사용자의 온라인/오프라인 메뉴얼 불일치
- 요구사항 분석서와 기능 요구사항의 불일치로 인한 불완전한 상태의 문서


결함 심각도
- 여러 개의 결함 중 전체 시스템에 결함이 미치는 영향을 레벨별로 나타내는 것

High
- 시스템이 중단되어 더이상 프로세스를 진행할 수 없게 만드는 결함
- 핵심 요구사항 미구현, 시스템 다운, 장시간 시스템 응답 지연, 스템 복구 후 데이터 왜곡 등
Medium
- 시스템의 흐름에 영향을 미치는 결함
- 부정확한 기능, 부정확한 업무 프로세스, 데이터 필드 형식의 오류, 데이터베이스 에러, 보안 관련 오류
Low
- 시스템의 흐름에는 영향을 미치지 않는 결함이나 상황에 맞지 않는 용도와 화면 구성의 결함
- 부정확한 GUI 및 메시지, 에러 시미지 미출력, 화면상의 문법/ 철자 오류


결함 관리하기
1. 어플리케이션 테스트 수행으로 발견된 결함을 기록하고 분류
- 발견된 결함을 관리할 테스트 관리 양식을 작성
관리할 항목 정의
테스트 ID 항목 생성
테스트 시나리오명 항목 생성
테스트 케이스명
테스트 수행 결과
테스트 담당자, 계획일, 수행일 항목을 생성
결함 내용 항목
추가하고 싶은 내용이 있다면 추가

- 기록된 테스트 관리 양식의 결함을 유형별로 분류하고 결함 상태를 확인한다
분석 : 요구사항의 표준 미준수, 테스트 불가능, 불명확
설계 : 설계 표준 미준수, 테스트 불가능, 불명확, 불일치
개발 : 개발 표준 미준수, 불완전, 불일치, 인터페이스 결함
테스트 : 업무 이해 부족, 팀 간 의사소통 부족, 개발자 실수

발생한 결함에 대한 결함 상태를 정의
Open
Assigned
Fixed
Closed
Deferred
Clarified

정의한 결함 유형을 이용하여 결함관리 현황을 결함관리표에 결함 상태를 같이 작성한다

2. 결함에 대한 윈인을 분석하고 개선 방안을 도출한다
- 발생한 결함에 대하여 결함 원인을 분석한다
ㄴ 테스트 종료 후 결함 데이터를 통합
ㄴ 통합된 결함 데이터를 분석하여 유사한 결함 형태로 정리
ㄴ 프로젝트 영역별로 결함 원인을 표로 정리한다
분석 : 불명확한 요구사항으로 개발자의 업무에 대한 이해부족
설계 : 설계 내용 오류로 인한 불완전한 설계와 설계 문서에 대한 이해 부족
구현 : 설계에 대한 미실시와 개발자 능력 미숙, 불완전한 컴포넌트와 개발 도구 사용 미숙,
불완전한 테스트 데이터 사용
기타/공통 : 변경 사항 반영 미흡과 개발 표준 미준수

결함 종류를 식별하기 위해 원인 분석 도구를 사용한다
- 파레토 다이어그램
ㄴ 결함의 모든 요소를 목록으로 작성한다
ㄴ 결함과 관련된 요소들을 측정한다
ㄴ 결함 수가 가장 높은 순에서 낮은 순으로 작성한다
ㄴ 결함 항목에 대한 백문율을 계산한다
ㄴ 자료값을 이용하여 각 범주를 나타내는 막대를 그린다
ㄴ 누적 백뷴율을 파레트 차트에 표시한다
-피시본 다이어그램
ㄴ 결함의 주요 원인을 확인
ㄴ 결함의 잠재적 원인을 팀원들과 브레인스토밍한다
ㄴ 결함의 범주를 나누고 항목에 따라 잠재적 원인을 추가
ㄴ 팀원들과 질문을 계속하여 검증하고, 추가적인 내용을 더 제시하도록 한다
ㄴ 결함 항목을 검토하고 항목 중에서 가장 가능성이 높은 원인을 팀원들과 브레인스토밍 등의
방법으로 도출하여 작성한다

2. 결함 관리의 이해
2-1. 결함 관련 용어
- 에러(Error)
ㄴ 소프트웨어 개발 또는 유지 보수 수행 중에 발생항 부정확한 결과로, 개발자의 실수로 발생한 오타, 
개발 명세서의 잘못된 이해, 서브루틴의 기능 오해 등이 있다.
- 오류(Fault)
ㄴ 프로그램 코드상에 존재하는 것으로 비정상적인 프로그램과 정상적인 프로그램 버전 간의
차이로 인하여 발생되며, 잘못된 연산자가 사용된 경우에 프로그램이 서브루틴으로부터의
에러 리턴을 점검하는 코드가 누락된 것
- 실패(Failure)
ㄴ 정상적인 프로그램과 비정상적인 프로그램의 실행 결과의 차이를 의미하며, 프로그램 실행 중에
프로그램의 실제 실행 결과를 개발 명세서에 정의된 예성 결과와 비교함으로써 발견한다
- 결함(Defect)
ㄴ 버그, 에러, 오류, 실패, 프로그램 실행에 대한 문제점, 프로그램 개선 사항 등의
전체를 포괄하는 용어
2-2. 결함 판단의 기준
- 기능 명세서에 가능하다고 명시된 동작을 수행하지 않는 경우
- 기능 명세서에 불가능하다고 명시된 동작을 수행하는 경우
- 기능 명세서에 명시되어 있지 않은 동작을 수행하는 경우
- 기능 명세서에 명시되어 있지 않으면 수행해야 하는 동작을 수행하지 않는 경우
- 테스터의 시각에서 볼 때 문제가 있다고 판단되는 경우

테스터의 시각에서 결함으로 판단되는 경우
이해하기 어려운 기능, 사용이 까다로운 기능, 비정상적으로 느린 기능 등

3. 테스트 격언
3-1. 소프트웨어를 완벽하게 테스트하는것은 불가능하다
- 가능한 입력의 수가 너무 많다
- 가능한 출력의 수가 너무 많다
- 소프트웨어 명세서가 주관적이라
- 소프트웨어 결함도 중요도 이다.
3-2. 소프트웨어 테스틑 위험을 수반하는 훈련이다
- 가능한 모든 테스트 시나이로와 테스트 케이스를 테스트하지 않을 경우 위험을
감수하고 하기도 했다는 뜻과 같아
- 테스터는 무엇이 중요하고, 중요하지 않은지 현명한 판단을 해야 한다
3-3. 테스트 작업으로 결하이 존재하지 않은다는 사실을 입증할 수 없으면,
단지 테스트 결과로 결함이 있다는 사실만으로 의미하는 것은 아니다
3-4. 아래와 같은 사유로 인하여 발견된 모든 결함을 수정할 수는 없다
- 쫓기는 외부 일정
- 외부적 요인으로 결함이 아님에도 결함으로 판된되는 경우
- 각각의 프로그램 간에 서로 결합도가 높은 경우우의 고치기 

3-5. 발결한 결함치 많을수록 남아있는 결함하는 훈련이다
