# ⚙️ 통합 구현 (Integration Implementation)

## 📌 1. 통합 구현의 개요 및 필요성

### 🔄 이기종(Different) 시스템 간 데이터 연계 필요성 증가
* 자체 개발 서비스(쇼핑몰, 게시판 등)와 기업 비즈니스 핵심 솔루션 간의 데이터 결합이 필수적입니다.
  * **ERP (기업 자원 관리):** 회사의 모든 자원과 업무를 하나의 시스템으로 통합 관리
  * **CRM (고객 관계 관리):** 고객 데이터 분석 및 관리 시스템
  * **모바일/웹 인터페이스:** 다양한 프론트엔드 환경과의 실시간 연동

### 🚀 서비스 확장성 및 재사용성 확보
* 새로운 채널이나 디바이스가 추가되더라도 기존 시스템의 변경을 최소화합니다.
* **예시:** 웹 중심 서비스에 **모바일 앱**을 추가하거나 오프라인 **키오스크**를 추가할 때 유연한 연동 구조를 보장합니다.

### ⚡ 운영 효율성 및 데이터 품질 향상
* 통합 구현을 통해 데이터를 자동으로 전달하면 처리 속도가 빨라집니다.
* 수작업 오류(Human Error)가 줄어들어 데이터의 정확성과 신뢰성이 극대화됩니다.

### 💡 데이터 조합을 통한 신규 서비스 창출
* 여러 시스템에 파편화되어 있는 데이터를 하나로 결합합니다.
* 모인 데이터를 바탕으로 새로운 통계 정보를 추출하거나 차별화된 신규 비즈니스 모델을 제공할 수 있습니다.

## 🔍 2. 연계 요구사항 분석 및 표준화

### 📋 연계 요구사항 분석 단계
시스템을 실제 연결하기 전, 어떤 데이터를 어떤 방식으로 주고받을지 면밀히 분석하는 설계의 핵심 기초 단계입니다.
* **주요 입력 산출물:** `시스템 구성도`, `응용 어플리케이션 구성도`, `ERD(개체-관계 다이어그램)`, `테이블 정의서`
* **분석 4단계 절차:**
  1. **현행 시스템 환경 파악:** `H/W`, `S/W`, `N/W`, `DB`, `ERD` 인프라 구조 확인
  2. **사용자 요구사항 수집:** `인터뷰`, `설문`, `체크리스트`, `FGI`, `델파이 기법` 활용
  3. **연계 데이터 분석:** 데이터 형식, 변환 규격, 보안 요구사항 및 솔루션 검토
  4. **결과 정리 및 문서화:** `요구사항 분석서`, `인터페이스 정의서`, `회의록` 작성

### 🎯 연계 데이터 식별 및 표준화 절차
시스템마다 동일한 정보를 관리하더라도 컬럼명, 데이터 길이, 코드 체계 등이 다르므로 사전에 동일한 규격으로 정의하는 작업이 필요합니다.
1. **송/수신 데이터 식별:** 테이블 및 코드 정의서를 분석하여 연계에 필요한 컬럼을 추출하고 `타입`, `길이`, `PK 여부`, `NULL 허용 여부`를 확인합니다.
2. **연계 데이터 형식 정의:** 시스템 환경 및 솔루션 특성에 맞춰 최적의 포맷을 선정합니다.
   * **`JSON`:** 가장 표준적으로 널리 사용됨 (경량, 높은 가독성)
   * **`XML`:** 공공기관이나 레거시(Legacy) 시스템 연계 시 주로 활용
   * **`CSV / TEXT`:** 대용량 파일 연계 또는 단순 데이터 전송 시 활용
3. **코드 체계 매핑:** 송/수신 시스템 간 공통 코드가 다를 경우 일대일 상호 변환 규칙을 수립합니다.

### 📋 데이터 표준화 3대 필수 점검 사항
* **구조 매핑:** 서로 다른 항목명을 1:1로 매핑하여 일치시킵니다. (예: `name` ──> `userName`)
* **길이 정합성 검토:** 송신측 길이가 수신측 저장소보다 긴 경우 데이터가 잘리는 손실(`Truncate`) 위험이 있으므로 사전에 크기를 조정합니다.
* **데이터 정제 기준 마련:** 수신 DB 저장 전 품질을 높이기 위한 정제 규칙을 적용합니다. (예: 공백/중복 제거, `NULL` 처리, 날짜 포맷 통일)

## ⚙️ 3. 상세 연계 메커니즘 및 DB 반영 절차

### 🧭 연계 메커니즘 설계 4단계

데이터 형식, 전송 방식, 보안, 신뢰성을 종합 고려하여 애플리케이션과 외부 모듈 간에 데이터를 안정적으로 교환하는 기술적 체계입니다.

#### ① 구성요소 파악 (송/수신 내부 컴포넌트 식별)
* **송신 시스템:** 데이터 추출 프로그램(`SQL`, `Batch`, `CDC`), 전송 이력을 기록하는 로그 관리, 실패 시 예외 상황에 대응하는 에러 처리 로직으로 구성됩니다.
* **수신 시스템:** 수신한 데이터의 규격을 맞추는 데이터 변환 로직, 운영 DB에 반영하는 적재 프로그램, 실패 건을 격리 관리하는 에러 및 재처리 로직, 최종 반영 테이블로 구성됩니다.

#### ② 연계 서버 및 연계 방식 정의
* **연계 서버의 역할:** 송/수신 시스템 간의 중계자(미들웨어)로, 이기종 간 포맷/프로토콜 변환, 메시지 라우팅, 보안 통제(암호화 및 인증/인가)를 수행합니다.
* **연계 방식 선택 기준:**
  * **실시간 처리:** 즉각적인 응답 및 이벤트 동기화 필요 시 채택 (`REST API`, `Socket`, `Event-Driven`)
  * **대용량/비실시간 처리:** 정기적인 대량 데이터 전송 필요 시 채택 (`FTP/SFTP`, `DB Link`, `DB Connection`)

#### ③ 인터페이스 테이블 및 임시 영역 정의
* **목적:** 송/수신 시스템 간의 스키마 구조 차이 및 데이터 생성/전송 주기 격차를 완화하는 버퍼 구역입니다.
* **기능:** 최종 DB에 바로 기록하지 않고 임시 영역에 저장함으로써 데이터 유효성 검증 및 가공 처리를 안전하게 진행합니다.

#### ④ 로깅 및 장애 복구 계획 정의
* **로그 관리 목적:** 실시간 모니터링, `SLA` 준수 검증, 보안 감사 대응, 장애 발생 시 원인 추적성 확보
* **재처리 메커니즘:** 데이터 전송/적재 실패 시 전체 파이프라인을 멈추지 않고, **실패한 데이터 건만 선별하여 다시 전송**하는 복구 체계를 구축합니다.

### 💡 데이터 생성/추출 핵심 고려사항
* **데이터 품질:** 원천 데이터 추출 단계부터 데이터 누락, 왜곡, 중복 발생을 원천 차단합니다.
* **성능 최적화:** 원천 DB 부하를 줄이기 위해 적절한 배치 주기, 추출 데이터 범위 및 인덱스 검색 조건을 최적화합니다.
* **운영 안정성:** 로깅 시스템 연동 및 중복 전송 방지(Idempotency, 멱등성) 로직을 탑재합니다.

## 📊 4. 대규모 데이터 및 모니터링 아키텍처

### 🔄 고성능 데이터 추출 및 적재 패러다임
* **`CDC` (Change Data Capture):** DB의 변경(CUD) 이력만을 실시간 감지하여 추출하는 기술입니다. 전체 수집(Full Dump) 방식 대비 시스템 부하가 매우 적어 실시간 동기화에 최적화되어 있습니다.
* **`Data Warehouse` (데이터 웨어하우스):** 여러 운영 시스템으로부터 데이터를 추출·변환·적재하여 한곳에 모아둔 분석 전용 대용량 데이터베이스 저장소입니다.

### 🗂️ 데이터 웨어하우스 구축 파이프라인 비교

| 비교 항목 | 🗂️ ETL (Extract, Transform, Load) | 🚀 ELT (Extract, Load, Transform) |
| :--- | :--- | :--- |
| **핵심 메커니즘** | 추출 후 **정제·가공을 먼저 완료**하고 적재 | 추출 후 **원본을 그대로 먼저 적재**하고 필요 시 가공 |
| **처리 방식** | 데이터 변환 처리를 별도의 스테이징 영역에서 마친 후 최종 시스템 전송 | 대용량 클라우드 저장소에 원본을 선적재한 뒤, 고성능 클라우드 분석 엔진 성능으로 필터링 및 변환 |
| **인프라 특징** | 타겟 시스템의 연산 부담 최소화, 데이터 구조 명확 | 현대적 클라우드 환경에 최적화, 유연한 원본 데이터 보존 |

### 🚀 분산 메시징 및 이벤트 스트리밍 플랫폼
* **`Kafka`:** 고성능 분산 이벤트 스트리밍 플랫폼입니다. 메시지를 메모리뿐만 아니라 **디스크에 순차적으로 저장(Append-only)**하므로 높은 데이터 신뢰성을 보장합니다.
* **`Pulsar`:** 멀티테넌시 구조와 컴퓨팅-저장소 분리 아키텍처를 지원하는 차세대 분산 메시징 및 스트리밍 플랫폼입니다.
* **저장 포맷 최적화:**
  * **`Avro`:** 데이터를 가로(Row) 방향으로 차곡차곡 모아서 저장하는 행 중심 포맷입니다.
  * **`Parquet` (파케):** 데이터를 세로(Column) 방향으로 그룹화하여 저장하는 열 중심 포맷으로, 압축률과 특정 컬럼 분석 효율이 매우 뛰어납니다.

### 👁️ 관제 솔루션 및 서비스 품질 관리
* **`ELK 스택`:** `Logstash`(수집·가공) + `Elasticsearch`(검색·분석) + `Kibana`(시각화) 조합의 대용량 로그 관리 특화 스택입니다.
* **`Grafana`:** 시각화 및 데이터 분석 대시보드에 최적화된 오픈소스 플랫폼으로 시계열 데이터 관제에 널리 쓰입니다.
* **`AWS CloudWatch`:** AWS 인프라 환경에서 리소스 상태와 어플리케이션 로그를 실시간 관리하는 일체형 모니터링 서비스입니다.
* **`QoS` (Quality of Service):** 네트워크 자원이 한정된 상황에서 중요 데이터 트래픽에 우선순위를 부여하여 비즈니스 핵심 서비스의 성능과 신뢰성을 보장하는 통제 메커니즘입니다.

## 🛡️ 5. 최신 API 패러다임 및 엔터프라이즈 보안

### 🔌 통신 유형 및 기술 분류
* **실시간 API:** 클라이언트가 데이터를 요청하면 중간 매개체 없이 서버가 즉시 응답하는 1:1 대화 방식입니다.
* **메시지 큐 (MQ):** 송신자가 대기열(Queue)에 작업을 넣으면 수신자가 하나씩 꺼내 처리하는 1:1 번호표 창구 방식입니다. (시스템 간 비동기 결합도 완화)
* **이벤트 스트리밍:** 시스템에서 발생하는 모든 상태 변화를 연속적인 데이터 흐름(Stream)으로 취급하여 실시간 수집·분석합니다.
* **`Pub/Sub` (발행/구독):** 발행자(`Publisher`)가 특정 주제(`Topic`)에 메시지를 내보내면, 이를 구독 중인 다수의 수신자(`Subscriber`)에게 데이터가 동시 분산 전달되는 1:N 방식입니다.

### 🌐 웹 API 패러다임의 변화

#### 🚨 기존 REST API의 한계와 단점
1. **설계 표준의 한계:** 강제적인 공식 표준 규약이 없어 개발자나 조직마다 아키텍처 설계 방식이 파편화될 수 있습니다.
2. **데이터 전송의 비효율성:** 불필요한 데이터까지 응답받는 오버페칭(`Over-fetching`) 문제와, 필요한 데이터를 위해 여러 번 API를 호출해야 하는 언더페칭(`Under-fetching`) 문제가 존재합니다.
3. **구조적 제약:** 무상태성(`Stateless`) 제약으로 매 요청마다 인증 정보를 중복 전송해야 하므로 통신량이 증가하며, 제한적인 HTTP 메서드 사용으로 복잡한 연산 표현이 까다롭습니다.

#### 💡 차세대 대안 기술 및 금융 표준 규격
* **`GraphQL`:** Meta에서 개발한 데이터 쿼리 언어입니다. 클라이언트가 **자신이 필요한 데이터 구조만 콕 집어서 요청**할 수 있어 REST API의 비효율성(Over/Under-fetching)을 완벽하게 해결합니다.
* **`AsyncAPI`:** 동기식 REST API 명세(OpenAPI)를 이벤트 기반의 비동기/메시징 아키텍처(Kafka 등) 프로토콜 영역으로 확장하여 정의한 표준 명세서입니다.
* **`오픈 API`:** 기업이나 기관이 내부 시스템 데이터나 기능을 외부 개발자가 활용할 수 있도록 개방한 인터페이스입니다.
* **`ISO 20022`:** XML, JSON 기반으로 제정되어 전 세계 금융망(은행, 증권 등) 간에 데이터 손실 없이 정확한 결제 메시지를 교환하도록 보장하는 글로벌 표준 규격입니다.

### 🛡️ 엔터프라이즈 관리 인프라 및 보안 기술

#### 🔑 OAuth2 (Open Authorization 2.0)
사용자가 비밀번호를 직접 입력하거나 제3자 앱에 노출하지 않고도, 인증 서버를 통해 권한을 안전하게 위임(Authorization)받아 데이터에 접근할 수 있도록 지원하는 프레임워크이며, 현대 **소셜 로그인(Google, Kakao, Apple 등)의 핵심 기반 기술**입니다.

* **OAuth2의 4가지 핵심 구성 요소 (Roles):**
  1. **Resource Owner (자원 소유자):** 서비스를 이용하는 실제 **사용자(User)**이자 계정 데이터의 주인입니다.
  2. **Client (클라이언트):** 사용자의 인증 권한을 획득하여 특정 서비스를 제공하려는 **신규 앱 / 웹 서비스**입니다.
  3. **Authorization Server (인증 서버):** Resource Owner를 인증하고 권한이 확인되면 Client에게 **Access Token을 발급**하는 서버입니다.
  4. **Resource Server (자원 서버):** 사용자의 실제 데이터를 보관하는 저장소이며, Access Token의 유효성을 검증하여 데이터를 Client에 응답합니다.

#### 🏢 API 관리 및 라우팅 솔루션
* **`Kong`:** 경량화와 뛰어난 성능을 자랑하는 클라우드 네이티브 환경 중심의 대표적인 고성능 API Gateway 솔루션입니다.
* **`Apigee`:** 구글 클라우드가 제공하는 기업용 풀스택 API 관리 플랫폼으로, 설계·보안·모니터링부터 API 수익화까지 전체 생명주기를 관리합니다.
* **`NGINX`:** 트래픽이 몰리는 대용량 환경을 효율적으로 처리하기 위해 고안된 비동기 이벤트 기반의 고성능 웹 서버이자 리버스 프록시입니다.
* **`WSO2`:** 오픈소스 기반으로 통합 API 관리, 식별·인증·인가(Identity), 연계 미들웨어 기능을 일체형으로 제공하는 통합 플랫폼입니다.
